Tabs presents one active panel from a labeled set with documented selection, keyboard navigation, focus, and accessibility behavior.

Overview

Use Tabs when several peer sections share one region and users should switch between them without navigating to another location. A Tabs instance contains a root, tablist, tabs, and corresponding tabpanels.

When to use and alternatives

Use Tabs for peer panels inside one task or content region when switching panels is not destination navigation. Do not use Tabs as an application router, breadcrumb substitute, side navigation, or generic segmented control. If the choices are form values rather than panels, use the appropriate selection control instead.

Anatomy

A Tabs instance contains one root, one tablist, one or more tabs, and one corresponding tabpanel per tab. Tabs and panels are connected through their documented values and accessible relationships.

Variants and sizes

Tabs has no size variants in this channel. Configure behavior with orientation and activation mode.

State

Selection and keyboard focus are distinct. The selected tab exposes aria-selected="true"; disabled tabs expose aria-disabled="true" and are skipped during keyboard movement. Inactive panels are hidden. The selected value is externally meaningful; focus position remains managed interaction state.

Behavior

Automatic activation selects a tab when keyboard focus moves to it. Manual activation keeps focus and selection separate until Enter or Space is pressed. Pointer activation selects an enabled tab in either mode. A requested selection remains distinct from committed controlled state.

Interaction

Horizontal tablists use Left and Right Arrow; vertical tablists use Up and Down Arrow. Home moves to the first enabled tab and End to the last. Navigation wraps and skips disabled tabs. Horizontal arrow mapping follows text direction.

Accessibility

Give every tablist an accessible name with aria-label or aria-labelledby. Every tab must identify its panel and every panel must identify its tab. Keep focus indication visually distinct from selected styling. Tabs uses the accepted custom tab interaction model with roving focus and documented activation policy; application authors own meaningful tab labels and panel content.

Responsive and platform adaptation

Responsive layout may change spacing, wrapping strategy, or surrounding composition, but it must preserve logical order, tab/panel relationships, selected value, focus visibility, and keyboard behavior. A cramped Web layout is not permission to silently replace Tabs with unrelated navigation. Native-platform products may choose a platform-native peer-section pattern while preserving the same task meaning; that does not create a VyrnForge native renderer.

Loading and async ownership

Tabs does not own application loading, fetching, retry, or persistence state. Individual panels may compose loading/status patterns and application data services, but those states must not be collapsed into tab selection or disabled semantics.

Error and validation

Tabs has no generic error or validation state. A panel may contain forms or task errors under their own contracts. Do not color a tab as an “error tab” and assume that visual state alone communicates the affected problem; any such application composition needs an explicit semantic/content contract.

Content and localization

Consumers author concise tab labels and panel content. Labels must remain localizable and should tolerate text expansion without destroying focus order or relationships. Direction-aware keyboard behavior follows the document/component direction contract; VyrnForge does not introduce hidden English labels.

Forms

Tabs does not define form values, validation, submission, or reset behavior. Place form controls inside tabpanels according to the controls' own documentation.

Styling

Stable hooks are data-vf-tabs-root, data-vf-tabs-list, data-vf-tabs-tab, and data-vf-tabs-panel, along with documented state hooks for selection, disabled state, orientation, and activation. Prefer public --vf-* tokens and stable hooks for customization.

CSR and SSR

React, Angular, and Vue can render tab roles, selection, panel visibility, and relationships during SSR and hydrate those relationships before post-activation interaction. Elements becomes interactive after explicit registration and browser upgrade. Existing representative browser evidence covers actual hydration/activation for Tabs in its recorded scope; it does not imply every VyrnForge component is hydration-tested.

Implementation and evidence status

Tabs is an implemented compound Web component concept across React, Angular, Vue, and Elements, with canonical styling owned by Web. Accepted accessibility mapping identifies tab semantics, roving focus, orientation/RTL behavior, and activation policy. Existing protected browser evidence demonstrates representative SSR/hydration or upgrade plus post-activation behavior for the declared surfaces. Manual assistive-technology evidence remains a separate requirement where spoken interoperability is claimed.

Do / Don't

Do use Tabs for peer sections, provide an accessible tablist name, and keep tab labels concise. Don't use Tabs as application routing or recreate its keyboard behavior with application-specific handlers.

Testing guidance

Query by role and accessible name, assert selected state and visible panel outcomes, and test keyboard movement, disabled skipping, wrapping, Home/End, activation mode, orientation, directionality, browser focus, controlled-owner acceptance/rejection where applicable, and activation without phantom selection intent.

Compatibility and migration

Tabs is documented for React, Angular, Vue, and Elements in this channel. Documented anatomy, selection semantics, activation/orientation policy, intent events, accessibility relationships, public styling hooks, and entrypoints are compatibility commitments. Framework grammar remains idiomatic and is not required to be identical across ports. See the Compatibility reference for validated runtime/browser ranges.
