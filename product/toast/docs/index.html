Toast provides a polite notification viewport and dismissible notification anatomy without owning application messaging queues, severity policy, persistence, or domain events.

Overview

Use Toast for transient, non-blocking status messages. Routine notifications use polite status semantics and do not move focus automatically.

When to use and alternatives

Use Toast for concise supplemental status that can disappear without removing the user's only access to information or an essential action. Use inline task feedback when recovery remains relevant to the current control or region, a persistent banner for broader page/product context, an application-owned inbox when durable history matters, or Dialog/AlertDialog when a focused decision is genuinely required. Do not use Toast as the sole location for unresolved validation, required retry, permission instructions, unknown mutation outcomes, or irreversible deadlines.

Installation and imports

Import from each framework's /toast subpath and load @vyrnforge/web/styles/toast.css. Elements registers vf-toast and vf-toast-viewport explicitly; importing the module does not register them globally.

Quick start

Anatomy

Viewport, root, title, description, and an optional native-button close control. The close control has no library-authored English label; provide visible button text or an authored aria-label/aria-labelledby when the control is icon-only.

State ownership

open is externally meaningful state. When supplied, it is authoritative: close and timeout interactions request false, but the Toast stays visible until the owner commits the closed state. When open is absent, the port owns local state initialized once from defaultOpen, which defaults to true. Later default changes do not reset live uncontrolled state.

Duration and pause behavior

The default duration is 5000 ms. duration=0 is persistent. Only a finite positive duration arms a timer; negative or non-finite runtime values behave persistently. A changed positive duration restarts the current open cycle with that duration, while ordinary rerenders or callback identity changes do not reset the deadline.

Finite timers pause while pointer hover or keyboard focus is inside the Toast. Hover and focus are independent pause reasons, so timing resumes only after both have cleared. A duration change while paused replaces the remaining duration but remains paused. Closing, unmounting, or disconnecting clears the old timer; a real close followed by reopen starts a fresh full duration. Timers start only after client activation.

Close behavior

Close remains a native button and uses native Enter/Space activation. One activation requests one close transition. A supported consumer click handler may cancel the request with preventDefault(). Vue retains its dismiss notification for compatibility while root state changes through the root open-change contract.

Elements migration

New timed or controlled Elements usage should register and use vf-toast as the state-owning root. The existing vf-toast-viewport registration signature remains supported. Legacy authored [data-vf-toast-root] content inside the viewport keeps uncontrolled close behavior without DOM deletion; migrate it to vf-toast when controlled state, timeout, or pause behavior is required.

Accessibility

The viewport uses polite live-region semantics and each Toast root uses status semantics by default. Consumers own meaningful notification content and close-control names. DOM and automated accessibility assertions verify semantic wiring; they do not establish that a particular screen reader spoke a particular message. Manual assistive-technology evidence remains a separate review boundary.

Responsive and platform adaptation

Toast presentation must remain usable under narrow layouts, zoom/reflow, text expansion, direction changes, keyboard focus, and pointer/touch interaction without obscuring required task access. Placement may adapt to the Web layout or to a platform-native notification convention, but message meaning, persistence needs, available actions, and focus expectations must remain intact. This Web component does not imply a native mobile or desktop renderer.

Loading and async ownership

Toast may communicate an asynchronous outcome after the owning operation state is known, but it is not an operation controller, request queue, retry engine, persistence store, or source of truth. Do not announce success before authoritative commit. Background-task state and durable recovery remain owned by the application and the Async/Error contracts.

Error and validation

Error severity does not automatically select Toast. Validation errors, permission guidance, required retry, partial failure, and unknown outcomes require an appropriate durable owning surface. A Toast may supplement those surfaces when useful, but dismissal of the Toast must not erase or resolve the underlying condition.

Content and localization

Consumers author truthful, localizable notification text and any close-control label. VyrnForge does not provide hidden English fallbacks or a built-in severity vocabulary inside Toast. Localized expansion may make a Toast unsuitable for essential or complex detail; prefer a concise status plus a durable destination rather than truncating required meaning.

Timing responsibility

A five-second default is component policy, not permission to remove the only access to essential information or an action. Use a persistent Toast or provide equivalent durable access when the notification contains information or an action that would otherwise disappear before the user can use it.

Consumer boundary

The application owns queueing, message text, translation, severity policy, persistence/history, business actions, retries, and domain-event handling. Toast does not introduce an application notification service or global state runtime.

Forms

Toast is not form-associated.

Styling

Canonical CSS is Web-owned and token driven. Stable styling and state hooks are compatibility commitments only where documented; application notification placement/policy should not depend on private Toast DOM structure.

Framework API

React exposes open, defaultOpen, duration, and onOpenChange. Angular exposes open, defaultOpen, duration, and openChange through directives. Vue exposes open, defaultOpen, duration, update:open, and openChange, while retaining dismiss on the close control for compatibility. Elements exposes VfToastElement/defineToastElement, the open, defaultOpen, and duration properties, and vf-open-change; defineToastViewportElement keeps its existing signature.

CSR and SSR

React, Angular, and Vue imports and semantic server rendering are server safe in the accepted Toast scope. Browser timers and interaction listeners begin only after activation. Elements uses explicit upgrade/connection/disconnection behavior rather than a framework SSR contract. These statements do not imply blanket hydration support for unrelated components.

Implementation and evidence status

Toast is implemented across the declared React, Angular, Vue, and Elements Web ports with canonical CSS owned by Web. The accepted #968/#981 repair remains the implementation/browser baseline for controlled and uncontrolled state, duration/pause behavior, close semantics, localized naming, teardown, and scoped SSR/server-safety evidence. It does not prove application notification selection, queue/history behavior, manual spoken-announcement interoperability, production delivery, or release readiness.

Testing guidance

Test controlled acceptance/rejection, uncontrolled close, close/reopen timing, duration changes, rerender stability, rejected timeout intent, overlapping hover/focus pause, click cancellation, ownership isolation, localized naming, live-region semantics, teardown, SSR/activation, public types, and package entrypoints. Keep manual assistive-technology observations separate from automated semantic assertions.

Compatibility

React, Angular, Vue, and Elements implement the same state, timing, close, and naming semantics through idiomatic APIs. Observable behavior is shared; lifecycle and state execution remain port-local. The additive vf-toast Elements root and existing viewport migration path remain as documented by the accepted Toast change. Documented state/intent/timing semantics, public entrypoints, and authored naming responsibilities are compatibility commitments; internal timers, contexts, and implementation structure are not. Any future compatibility change must state its migration impact explicitly.
