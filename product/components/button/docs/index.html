Button triggers an action or command while preserving native <button> semantics, keyboard activation, focus, and form behavior.

Actions Native-backed React · Angular · Vue · Native Web

Overview

Use Button when a user should perform an immediate action: save, confirm, submit, open an interface, retry, or cancel an operation. Button is deliberately native-first, so ordinary browser semantics remain the baseline rather than being reproduced with a custom controller.

Use Button

For actions and commands whose primary intent is activation.

Use something else

For navigation, use Link or a native anchor. Do not turn a generic element into a button only to achieve a visual style.

Quick start

The example below uses the same Button contract across every implemented framework surface. Switch framework tabs to compare idiomatic usage, or reveal the source when you want to edit and run it.

Variants and sizes

Variant communicates visual emphasis without changing the activation contract. Use primary for the strongest action, secondary for an alternative action, and ghost for lower-emphasis actions.

Variants

Sizes

Button supports sm, md, and lg. Medium is the default.

State and loading

disabled and loading are independent. Disabled prevents activation using the native disabled attribute. Loading exposes busy state with aria-busy="true" but remains focusable and activatable unless you also disable the button.

Loading does not imply disabled. If repeat activation must be blocked while application work is in progress, set both states explicitly.

Interaction and forms

Pointer activation plus Enter and Space keyboard activation are supplied by the native button. VyrnForge does not add JavaScript key handling or a second activation event. Focus remains native and receives the canonical :focus-visible treatment.

Button also preserves native form participation. The baseline does not override the platform default type, so an omitted type inside a form can submit it. Use type="button" for non-submit actions and type="reset" for native reset behavior.

Accessibility

The semantic control is an actual <button>, so no explicit button role is needed. Provide an accessible name through visible content or an appropriate naming mechanism such as aria-label or aria-labelledby. VyrnForge does not generate fallback English labels.

  • disabled uses native disabled semantics rather than replacing them with aria-disabled.
  • loading preserves the accessible name and derives aria-busy="true".
  • The loading indicator is decorative and does not duplicate the accessible name.
  • Forced-colors, reduced-motion, LTR, and RTL behavior are handled by canonical Web styling.

Content and responsive use

Author concise action labels that describe what will happen. Icon-only content requires an authored accessible name; Button does not introduce a special icon-only API. Text expansion, bidirectional content, zoom, touch, pointer, and keyboard use must preserve the action meaning. Surrounding composition owns placement and wrapping.

Framework API

The semantic contract is shared; each framework exposes it idiomatically rather than cloning one framework's API grammar.

SurfaceButton API
ReactButton forwards native button props and ref and adds variant, size, and loading. Native onClick is activation.
AngularVfButtonDirective attaches to an actual <button vfButton>. Inputs map variant, size, loading, and disabled; native (click) remains activation.
VueButton renders a native button, exposes variant, size, and loading, forwards fallthrough native attributes, and uses the default slot for content.
Native WebAuthor a native <button data-vf-button> with the documented state/configuration attributes and public stylesheet.

Rendering and hydration

React, Angular, and Vue SSR output is native-complete before hydration for semantics, keyboard interaction, focus, disabled state, and forms. Hydration adds framework event wiring rather than replacing the semantic control. Native Web requires no hydration.

Testing guidance

Query Button by role and accessible name, then assert observable outcomes such as activation or form submission. Keep loading-state tests separate from disabled-state tests. Depend only on documented props, native attributes/events, public entrypoints, and stable styling hooks.

Compatibility

Button is implemented for Native Web, React, Angular, and Vue in this documentation channel. Its native semantics, variant/size/loading meanings, form behavior, public hooks, and shipped framework entrypoints are compatibility commitments. Custom Elements Button remains explicitly unavailable rather than shipping a weaker semantic substitute.

Use the Compatibility reference for validated framework, browser, and runtime ranges. Implementation and test evidence are scoped to the revisions and scenarios that recorded them; this page does not promote a broader release or production-maturity claim.
