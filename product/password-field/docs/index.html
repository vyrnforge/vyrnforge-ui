PasswordField composes a native password input with an explicit visibility control while leaving validation, strength policy, authentication, credential verification, and session policy to consumers.

Overview

Use PasswordField when users benefit from toggling password visibility. It is an input/presentation composite, not an authentication service.

Installation and imports

Import from each framework's /password-field subpath and load @vyrnforge/web/styles/password-field.css.

Quick start

Anatomy

Root, native input, and visibility toggle.

Variants and sizes

No password-policy variants.

State

Visibility is local presentation state; input value remains native. Authentication, reauthentication, session state, provider outcome, rate limits, and password policy remain application/provider state.

Behavior

The toggle switches the input between password and text presentation without changing the credential value. Applications should preserve native autocomplete, autofill, paste, and password-manager behavior unless an owning security policy documents a scoped exception.

Interaction

The toggle remains a native button.

Accessibility

The toggle exposes pressed state. Meaningful visibility-control wording and accessible naming must be authored/localizable; current cross-port fallback behavior is tracked separately by STD-15 repair #1040 and must not be treated as a localization contract.

Forms

Consumers own name, autocomplete, required state, validation, submission, verifier policy, and authentication execution. Use meaningful native credential autocomplete tokens when their semantics fit.

Identity workflows

Authentication flows distinguish credential entry from provider verification, session state, reauthentication, recovery, and authorization. VyrnForge does not provide an AuthProvider, token store, identity client, router guard, or WebAuthn/OAuth/OIDC/SAML implementation.

Styling

Canonical CSS is Web-owned and token driven.

Framework API

Ports expose the same input/toggle relationship idiomatically. Framework-specific state systems are not the shared identity contract.

CSR and SSR

Imports are server safe. Server rendering does not establish authentication or session truth.

Examples

The basic example demonstrates password visibility. The React-only session-recovery example is the STD-15 representative application workflow: a deterministic fake provider interrupts an unsaved edit, exposes passkey/SSO failure with a password fallback, then requires an OTP step before returning to the original task. It is UI-state evidence only and does not implement or prove provider/security behavior.

Do / Don't

Do preserve native credential semantics and task context when reauthentication is required. Don't embed authentication, password-strength policy, credentials, sessions, provider protocols, or authorization into PasswordField.

Testing guidance

Test input type, toggle state, authored naming, value preservation, SSR, and axe. Identity workflow evidence must state the fake/real provider boundary and must not be promoted into password-manager, passkey, SSO, OTP-delivery, or production-security claims.

Compatibility

React, Angular, Vue, and Elements implement the PasswordField concept. The complete STD-15 session-recovery workflow is currently a declared React representative example only; broader identity workflow support remains application/provider-owned and unclaimed.
