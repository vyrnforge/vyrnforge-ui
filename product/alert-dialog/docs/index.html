AlertDialog presents an interruptive modal decision that requires an explicit user response.

Overview

AlertDialog is a confirmation primitive for destructive or consequential decisions whose risk warrants interruption. It is not the default for every destructive action.

Choose the interaction from the actual risk and recovery model: low-risk actions should usually execute immediately; medium-risk actions should prefer real Undo or Restore when the product can honor it; high-risk actions with weak or no reversal should use explicit confirmation or review; critical actions may require explicit review plus independently implemented security, approval, or governance controls.

Installation and imports

Import the framework /alert-dialog subpath and Web CSS.

Quick start

Anatomy

Root, Title, Description, Body, Cancel, Action.

Variants and sizes

No semantic variants. Risk policy belongs to the consuming workflow rather than a visual AlertDialog variant.

State

Controlled or uncontrolled open state. A consuming workflow may keep open controlled while an application-owned destructive operation is pending or rejected.

Behavior

Uses Dialog modality but prevents backdrop dismissal. Cancel and Escape mean no destructive commit when dismissal is accepted by the consuming workflow.

AlertDialog does not own the destructive transaction. If an asynchronous commit is delayed or rejected, do not report success merely because the Action was activated. Consumers can prevent the Action close request or control open so decision and recovery context remains available until the application has authoritative commit truth.

Interaction

Escape may request dismissal; decision controls are explicit. Backdrop interaction does not dismiss destructive confirmation. Use an action label that names the real consequence, such as “Delete collection”, rather than a generic “Continue”.

Accessibility

Uses alertdialog semantics, labelled title/description, native modality and focus restoration. Consumers author the localized title, consequence description, recovery statement, Cancel label and action label; there are no hidden English defaults.

Forms

Consumers choose form semantics for authored actions.

Styling

Web-owned Dialog-derived CSS.

Framework API

Ports compose the shared Dialog contract. AlertDialog does not embed reauthentication, authorization, approval, retention, undo, recovery, or backend enforcement; those remain application, security, governance, or data responsibilities.

CSR and SSR

Imports are server safe; modal activation is client-only.

Examples

The basic example is a concrete high-risk shared-collection deletion with an explicit target, consequence, recovery status, and action label.

Do / Don't

Do select AlertDialog when risk and weak reversibility justify interruption; do preserve context until an application-owned commit is authoritative. Don’t put every delete behind a modal, fabricate Undo or recovery, close and announce success before a delayed commit succeeds, or move security/governance enforcement into AlertDialog.

Testing guidance

Test labeling, modality, Cancel/Escape behavior, blocked backdrop dismissal, delayed/rejected commit handling, focus restoration, SSR, and axe. Test application-owned transaction semantics separately from the reusable AlertDialog primitive.

Compatibility

React, Angular, Vue, and Elements.
