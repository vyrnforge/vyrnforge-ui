Button triggers an action or command while preserving native <button> semantics, form behavior, keyboard activation, and focus.

Overview

Use Button for actions such as saving, confirming, opening UI, or submitting a form. Use a link when the user is navigating to another location.

When to use and alternatives

Use Button when the user activates an action or command. Do not use it for destination navigation; use Link or a native anchor for that semantic. Do not replace native button activation with a custom div, generic ARIA controller, or application-specific keyboard handler merely for visual consistency.

Anatomy

Button has one semantic control: the button itself. Compose text, icons, and other inline content through your framework's normal content model.

Variants and sizes

Use primary for the strongest action, secondary for an alternative action, and ghost for lower-emphasis actions. Sizes are sm, md, and lg; md is the default.

State

disabled and loading are different states. Disabled prevents activation. Loading exposes busy state with aria-busy and a progress treatment but does not automatically disable the button. Set both when repeated activation must be prevented.

Behavior

Use the framework's normal click/event surface for activation. Button preserves native activation and form participation instead of adding a second activation event.

Interaction

Pointer activation and Enter/Space keyboard activation follow native button behavior. Keyboard-visible focus is styled with :focus-visible.

Accessibility

Provide an accessible name through visible content or an appropriate platform naming mechanism. Loading preserves the accessible name while exposing busy state. Reduced-motion and forced-colors treatments are included in the public stylesheet. Button is native-backed; an APG widget/controller abstraction is not required to reproduce behavior the platform already owns.

Responsive and platform adaptation

Button keeps the same action semantics under narrow layouts, zoom, touch, pointer, keyboard, and direction changes. Surrounding composition owns placement and wrapping; the component must not switch to a different semantic control merely because layout changes. Native mobile/desktop renderer support is not implied by the Web component.

Loading and async ownership

loading is a presentation/busy state, not an application request manager and not an automatic disabled policy. The consuming workflow owns operation truth, duplicate-submission policy, retries, cancellation, and authoritative success or failure.

Error and validation

Button has no generic invalid or error state. Form validation, operational failure, and recovery belong to the affected fields, form, task, or workflow. Error styling must not be invented on Button as a substitute for communicating the actual failure.

Content and localization

Consumers author the action label and its translation. Prefer concise visible labels that describe the action. Icon-only buttons require an authored accessible name; VyrnForge does not add a hidden English fallback. Text expansion and bidirectional content must remain usable without changing the action meaning.

Forms

Button preserves native form behavior. Native attributes such as type, name, value, form, and form override attributes remain available through the framework's native attribute surface.

Styling

Stable styling hooks are data-vf-button, data-vf-variant, data-vf-size, and data-vf-loading. Prefer documented --vf-* tokens and stable hooks when customizing Button.

CSR and SSR

React, Angular, and Vue render a native button during SSR and restore framework event handling during hydration. Native Web does not require hydration. These statements are component- and evidence-scoped; they do not imply every VyrnForge component has equivalent hydration evidence.

Implementation and evidence status

Button is an implemented native-backed Web concept on the declared Native Web, React, Angular, and Vue surfaces. An Elements wrapper is intentionally not required merely for catalog symmetry because native <button> already completes the semantic control. Existing native-control, accessibility, SSR, and browser evidence remains authoritative only for the revisions and scenarios that recorded it; this documentation does not promote release or production maturity.

Examples

The Quick start playground demonstrates the supported Button surfaces. Add application-specific composition around Button through ordinary framework patterns.

Do / Don't

Do use Button for actions and explicitly disable it when repeated activation must be blocked. Don't use Button as a navigation link or assume loading automatically prevents activation.

Testing guidance

Query Button by role and accessible name and assert observable outcomes such as activation or form submission. Depend only on documented props, events, attributes, and styling hooks. Test native form behavior and keep loading-state tests separate from disabled-state tests.

Compatibility

Button is documented for Native Web, React, Angular, and Vue in this channel. Documented native semantics, variant/size/loading options, form behavior, public hooks, and framework entrypoints are compatibility commitments. Internal implementation structure is not. Migration impact must be documented when those commitments change. See the Compatibility reference for validated runtime and browser ranges rather than inferring support from source presence.
