AppShell composes authored application regions without owning routing, authentication, data, permissions, privacy policy, or product workflow state.

Overview

Use AppShell for the stable application frame around authored header, navigation, main content, and optional footer regions. It standardizes shared structure and styling hooks while leaving product content and application policy to the consumer.

Installation and imports

Import from the framework-specific /app-shell subpath and load @vyrnforge/web/styles/app-shell.css, or load the aggregate @vyrnforge/web/styles.css.

Quick start

Navigation integration

Applications own URLs, route matching, browser-history policy, deep-link interpretation, page-title synchronization, route-change focus, not-found behavior, and return paths. Compose those concerns around AppShell and destination-oriented components rather than putting them into the shell. The representative settings example uses real AppShell, SideNav, Tabs, Button, and Drawer public entrypoints with a deliberately local history adapter: route changes update the title and main-view focus, a profile tab is URL-restorable without becoming primary navigation, a nested edit route has an explicit return target, and narrow presentation replaces the persistent rail with a Drawer while preserving the same destinations and current-page semantics.

Permission integration

Applications and their authorization services own capability evaluation, role or policy mapping, request-access workflows, permission refresh, impersonation policy, and authoritative enforcement. AppShell and Button may present the resulting authored UI, but hidden or disabled controls are never an authorization boundary. The representative permission example uses a deterministic application-local fake service to demonstrate capability-driven action presentation, an authoritative save denial despite previously allowed UI, preserved unsaved work, read-only recovery, request-access pending state, mid-task permission loss, and persistent impersonation context without adding a permission runtime to VyrnForge.

CRUD workflow integration

Applications and their services own resource models, persistence, transactions, concurrency, idempotency, routing, permissions, and import/export processing. Compose existing VyrnForge controls inside AppShell while keeping draft, pending, committed, failed, partial, and unknown outcomes truthful. Bulk operations need explicit selection scope and must preserve known successful subsets rather than retrying them. The representative item-management example uses real AppShell, Button, Input, and Checkbox public entrypoints plus an application-local deterministic fake service to demonstrate create, edit, reversible archive/restore, exact bulk selection, partial failure, durable mixed-result recovery, and unresolved-only retry without adding a CRUD store, controller, router, or transaction runtime to VyrnForge.

Privacy integration

Applications and accountable privacy/legal owners decide lawful or organizational basis, purposes, data classification, preference persistence, analytics/tracking/cookies, platform permission calls, retention, sharing, export, and deletion. AppShell, Button, and AlertDialog present authored privacy UI but do not determine compliance or enforce downstream processing. Valid optional privacy choices must remain discoverable without deceptive asymmetry, and browser/device permission prompts remain platform-owned. The representative privacy example uses deterministic application-local fake services to demonstrate equal optional-analytics choices and revocation, contextual camera-denial recovery, truthful export readiness, and account-deletion confirmation without adding a consent manager, cookie/analytics runtime, permission broker, privacy-policy engine, or deletion service to VyrnForge.

Anatomy

AppShell exposes authored Header, Body, Navigation, Main, and optional Footer regions. Header tools, search, account controls, breadcrumbs, and other product UI are composed as children rather than becoming shell configuration.

State

AppShell owns no route, authentication, tenant, permission, privacy preference, data, transaction, or application-workflow state. Consumers own those concerns and render the appropriate authored content into shell regions.

Behavior

The default shell fills the available viewport width and its body provides a navigation column plus flexible main content region, then collapses to one column at narrow viewport widths. Consumers that intentionally need a centered or capped application frame can set --vf-app-shell-max-inline-size. Applications that need overlay navigation should compose an accepted Drawer or other lower-layer surface instead of relying on a shell-specific overlay manager.

Accessibility

Use the semantic Header, Main, and Footer regions exposed by the framework port and preserve meaningful source order. Navigation content should contain its own named navigation landmark. AppShell does not invent hidden labels, reorder focus, or add positive tabindex values. Client-side route integrations should deliberately update document context and move focus only when the logical destination changes; local panel/filter/workflow updates should not reuse route-level focus behavior. Permission-aware integrations should preserve native disabled versus read-only distinctions, keep essential restricted-state explanations durable, and avoid treating ARIA state as either behavior or security enforcement. CRUD integrations should keep selection controls meaningfully named, preserve focus for routine same-surface outcomes, and expose durable partial-result recovery. Privacy integrations should keep equivalent valid choices keyboard-reachable and understandable, avoid stealing focus for routine preference updates, and must not visually simulate a native permission prompt as authoritative platform UI.

Styling

Canonical styling is owned by @vyrnforge/web, uses shared tokens and logical properties, and exposes data-vf-app-shell* hooks. AppShell is full-bleed by default; consumers may opt into a capped frame through the documented sizing custom property and may extend application-specific composition through ordinary CSS without replacing the shared semantic structure.

Framework API

React and Vue expose semantic region components, Angular exposes standalone directives on authored semantic hosts, and Elements exposes explicitly registered sibling custom elements. All ports implement the same region meanings without introducing framework-router, permission-policy, privacy-policy, data-store, or transaction types.

CSR and SSR

AppShell imports are server-safe. Static structural layout requires no client JavaScript; application-specific responsive overlays or product controls hydrate according to the lower-layer components they compose. Router/history, authorization, privacy preference/policy services, persistence, and transaction integration remain consumer-owned and must preserve native semantics without becoming an AppShell runtime.

Do / Don't

Do use AppShell for reusable application structure and compose route/history/title/focus, permission-aware presentation, resource workflows, and privacy controls at the application layer. Don't put router configuration, route guards, authentication, authorization policy, permission evaluation, privacy/legal policy, consent management, cookie/tracking/analytics execution, device-permission brokerage, retention/deletion services, tenant resolution, data fetching, persistence, CRUD stores, transaction coordination, import/export processing, or product workflow logic into the shell.

Testing guidance

Test landmark structure, semantic source order, full-bleed and intentionally capped desktop layouts, narrow layouts, LTR and RTL presentation, focus visibility, forced-colors behavior, SSR safety, and any composed responsive navigation behavior. Test route integrations separately for direct deep links, real link destinations, current-page semantics, title updates, route-level focus, Back/Forward restoration, local URL state, and return paths. Test permission-aware application integrations separately for capability-driven presentation, authoritative denial after optimistic or cached allowance, preserved work, read-only recovery, request-access status, impersonation context, and the keyboard/accessibility behavior of the exact composition. Test CRUD integrations for draft-versus-commit truth, exact bulk selection scope, committed/failed/unknown subsets, safe retry scoping, focus stability, and accessibility of the exact composition. Test privacy integrations for comparable valid choices, authoritative preference wording, withdrawal/revocation, denial/retry presentation, export completion truth, destructive confirmation/cancel focus restoration, and accessibility of the exact composition. UI/browser tests do not prove backend authorization, persistence, transaction, concurrency, idempotency, legal compliance, real analytics/tracking suppression, device-permission interoperability, or production export/deletion/retention correctness.

Compatibility

React, Angular, Vue, and Elements implement sibling AppShell ports, with Native Web providing the canonical shared CSS contract. The settings navigation, permission-access, item-management, and privacy-controls examples are representative React integration evidence only and do not claim router support, permission-engine support, CRUD/data runtime support, privacy/compliance runtime support, cross-port application integration, native-renderer support, or full Layer 6 acceptance.
