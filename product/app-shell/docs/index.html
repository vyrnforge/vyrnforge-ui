AppShell composes authored application regions without owning routing, authentication, data, permissions, or product workflow state.

Overview

Use AppShell for the stable application frame around authored header, navigation, main content, and optional footer regions. It standardizes shared structure and styling hooks while leaving product content and application policy to the consumer.

Installation and imports

Import from the framework-specific /app-shell subpath and load @vyrnforge/web/styles/app-shell.css, or load the aggregate @vyrnforge/web/styles.css.

Quick start

Navigation integration

Applications own URLs, route matching, browser-history policy, deep-link interpretation, page-title synchronization, route-change focus, not-found behavior, and return paths. Compose those concerns around AppShell and destination-oriented components rather than putting them into the shell. The representative settings example uses real AppShell, SideNav, Tabs, Button, and Drawer public entrypoints with a deliberately local history adapter: route changes update the title and main-view focus, a profile tab is URL-restorable without becoming primary navigation, a nested edit route has an explicit return target, and narrow presentation replaces the persistent rail with a Drawer while preserving the same destinations and current-page semantics.

Anatomy

AppShell exposes authored Header, Body, Navigation, Main, and optional Footer regions. Header tools, search, account controls, breadcrumbs, and other product UI are composed as children rather than becoming shell configuration.

State

AppShell owns no route, authentication, tenant, permission, or application-data state. Consumers own those concerns and render the appropriate authored content into shell regions.

Behavior

The default shell fills the available viewport width and its body provides a navigation column plus flexible main content region, then collapses to one column at narrow viewport widths. Consumers that intentionally need a centered or capped application frame can set --vf-app-shell-max-inline-size. Applications that need overlay navigation should compose an accepted Drawer or other lower-layer surface instead of relying on a shell-specific overlay manager.

Accessibility

Use the semantic Header, Main, and Footer regions exposed by the framework port and preserve meaningful source order. Navigation content should contain its own named navigation landmark. AppShell does not invent hidden labels, reorder focus, or add positive tabindex values. Client-side route integrations should deliberately update document context and move focus only when the logical destination changes; local panel/filter updates should not reuse route-level focus behavior.

Styling

Canonical styling is owned by @vyrnforge/web, uses shared tokens and logical properties, and exposes data-vf-app-shell* hooks. AppShell is full-bleed by default; consumers may opt into a capped frame through the documented sizing custom property and may extend application-specific composition through ordinary CSS without replacing the shared semantic structure.

Framework API

React and Vue expose semantic region components, Angular exposes standalone directives on authored semantic hosts, and Elements exposes explicitly registered sibling custom elements. All ports implement the same region meanings without introducing framework-router types.

CSR and SSR

AppShell imports are server-safe. Static structural layout requires no client JavaScript; application-specific responsive overlays or product controls hydrate according to the lower-layer components they compose. Router/history integration remains consumer-owned and must preserve deep links and native link behavior instead of becoming an AppShell runtime.

Do / Don't

Do use AppShell for reusable application structure and compose route/history/title/focus integration at the application layer. Don't put router configuration, route guards, authentication, authorization, tenant resolution, data fetching, application state, or product workflow logic into the shell.

Testing guidance

Test landmark structure, semantic source order, full-bleed and intentionally capped desktop layouts, narrow layouts, LTR and RTL presentation, focus visibility, forced-colors behavior, SSR safety, and any composed responsive navigation behavior. Test route integrations separately for direct deep links, real link destinations, current-page semantics, title updates, route-level focus, Back/Forward restoration, local URL state, and return paths without promoting those behaviors to AppShell ownership.

Compatibility

React, Angular, Vue, and Elements implement sibling AppShell ports, with Native Web providing the canonical shared CSS contract. The settings navigation example is representative React integration evidence only and does not claim router support, cross-port route integration, native-renderer support, or full Layer 6 acceptance.
