VyrnForge migrations are driven by documented public contracts, scoped change fragments, compatibility evidence, and versioned documentation. The rebuild channel is not yet a stable release, so this guide distinguishes current preview migration work from future stable upgrade guarantees.

Before upgrading

  1. Read the release or preview change summary for the version you are adopting.
  2. Check the Compatibility reference for the framework, browser, runtime, and SSR baseline associated with that documentation channel.
  3. Review the component pages you use for public API, styling hook, accessibility, and behavior changes.
  4. Run your application tests against the packed VyrnForge packages before promoting the upgrade.

Public compatibility boundary

Documented component properties, events or intents, exported subpaths, semantic tokens, documented component tokens, stable data attributes, and declared behavior are compatibility commitments once released. Private CSS aliases, internal helpers, generated implementation structure, and framework internals are not.

Rebuild preview migrations

The current next documentation channel describes a rebuild bootstrap rather than a stable upgrade path. Existing legacy APIs are not automatically preserved. Migrate only to surfaces documented in this channel, and treat missing compatibility claims as unavailable rather than implied.

Breaking changes

A future breaking release must document the old contract, the replacement contract, required consumer changes, and any temporary deprecation path. VyrnForge does not hide breaking semantic changes behind styling-only release notes.

Migration evidence

When a migration affects your application, validate the observable outcome: package imports, SSR/server rendering where relevant, keyboard and focus behavior, accessibility semantics, CSS/token overrides, and real-browser behavior. A successful type check alone is not migration proof.
