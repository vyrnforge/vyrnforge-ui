Use these diagnostics to distinguish package, styling, compatibility, documentation, and browser failures before changing component code. VyrnForge favors inspectable checks over hidden runtime diagnostics.

Foundation checks

npm run verify:foundation-readiness verifies the active token/CSS foundation, compatibility metadata, package-level lint evidence, and recorded browser qualification. npm run verify:tokens detects generated token CSS drift.

Targeted development checks

npm run check:changed:plan prints the impact-selected validation plan for local changes. npm run check:changed executes that plan. npm run check runs the broader main-tier validation when a foundation-wide result is required.

Styling problems

  • Confirm the application loaded either @vyrnforge/web/styles.css or every granular stylesheet required by the rendered components.
  • Check whether an application override changes a documented --vf-* token or ordinary CSS. Do not depend on undocumented implementation variables or internal selectors.
  • Do not assume the optional reset is included by the aggregate stylesheet; load it explicitly only when the application wants it.
  • Inspect the active data-vf-theme scope and inherited custom properties when nested themes do not render as expected.

Accessibility or interaction problems

Start from native semantics and the component contract. Verify roles, names, relationships, keyboard outcomes, focus behavior, disabled/read-only distinctions, reduced motion, and forced-colors behavior. Automated accessibility scans are guardrails, not a substitute for browser interaction evidence.

SSR or framework problems

Check the Compatibility reference first. Browser-only behavior must not execute during server rendering. Framework ports may differ in lifecycle and binding syntax while preserving the same observable VyrnForge contract.

Collecting a useful failure report

Include the VyrnForge documentation channel/version, framework and version, browser/runtime baseline, public import path, smallest reproduction, expected and actual behavior, and the failing validation command. For browser failures, attach the Playwright trace or screenshot when available.
