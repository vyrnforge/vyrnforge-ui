Typography gives content hierarchy, rhythm, and emphasis. VyrnForge provides a shared type scale and a small Text primitive so applications can use consistent visual roles without giving up native HTML semantics.

Choose semantics first. Pick the correct HTML element for meaning, then apply the VyrnForge typography role you want. A visual heading does not automatically become an h1–h6.

Overview

Text is VyrnForge's presentation layer for written content. It gives Native Web, React, Angular, and Vue the same role vocabulary—display, heading, title, body, label, caption, and overline—while keeping the underlying document structure explicit.

Use Text when

  • you want reusable visual hierarchy across products;
  • you want typography to follow shared VyrnForge tokens;
  • you need the same presentation vocabulary across supported framework ports.

Do not use Text to

  • replace semantic heading levels;
  • create form-label relationships;
  • encode disabled, invalid, selected, or other application state.

Installation and imports

The visual contract is owned by @vyrnforge/web. Load the canonical stylesheet once, then use the idiomatic Text surface for your framework where one exists.

Load the shared CSS

import '@vyrnforge/web/styles/text.css';

Native Web can then use the stable data-vf-text and data-vf-text-variant hooks directly.

Import the framework surface

// React
import { Text } from '@vyrnforge/react/text';

// Angular
import { VfTextDirective } from '@vyrnforge/angular/text';

// Vue
import { Text } from '@vyrnforge/vue/text';

Elements intentionally has no <vf-text> custom element. Native HTML already provides the semantic text elements, so Elements consumers use the Native Web contract.

Quick start

Start with the semantic element your document needs, then choose its visual role. Switch frameworks in the example below to see the same contract expressed idiomatically without changing the typography model.

Anatomy

Typography has two independent decisions: what the content means and how it should look. VyrnForge keeps those decisions visible instead of coupling them through an implicit heading map.

1

Semantic element

Choose h1–h6, p, label, strong, em, span, or another correct native element.

+
2

Visual role

Apply a role such as heading-lg, body-md, or label-sm. The role changes presentation only.

Same appearance, different meaning is possible. An h2 can use a quieter visual role and a paragraph can use a large display role. That flexibility is intentional, but semantic document structure remains your responsibility.

State

Text has no semantic state API of its own. Disabled, invalid, required, selected, pressed, busy, or other state belongs to the owning element or component.

Typography describes hierarchy, not state. Do not create variants such as disabled-text or error-heading when the actual state belongs to a Field, Button, alert, or another owning concept.

Behavior

Text applies token-driven typography to an opted-in native element and otherwise leaves document behavior unchanged. Display roles are fluid; the rest of the scale resolves directly from shared public typography tokens.

Fluid display typography

The display roles use CSS clamp(), so they grow with the viewport while remaining inside deliberate minimum and maximum sizes. No JavaScript resize listener or framework helper is involved.

Resize the browser and this display role adapts.
display-sm → clamp(--vf-font-size-2xl, 1.5rem + 2vw, --vf-font-size-4xl)

Relative units

The public size scale uses rem, which keeps browser text-size preferences in the sizing chain instead of hard-coding typography to device pixels.

Interaction

Text adds no pointer, keyboard, focus, selection, or event behavior. If text participates in an interaction, the native element or owning Button, Link, form control, or composite component remains responsible for that interaction contract.

Accessibility

Accessible typography starts with semantic structure. Visual hierarchy can reinforce meaning, but it cannot replace native document semantics.

Preserve heading hierarchy

Choose h1–h6 from the document outline you need. Then choose the visual role independently.

Respect user text sizing

VyrnForge's scale uses relative units so browser text-size preferences can continue to affect readable text.

Keep labels semantic

A label-looking span is not a form label. Use a real label and the proper control association when labeling form inputs.

Own contrast where color changes

Text inherits the active text color. If an application changes text or surface colors, the application remains responsible for maintaining readable contrast.

Forms

Text can style form-related copy, but it does not create form relationships. A real form label must remain a native label with the appropriate association.

Do

<label for="email" data-vf-text data-vf-text-variant="label-md">
  Email address
</label>
<input id="email" type="email" />

Don't

<span data-vf-text data-vf-text-variant="label-md">
  Email address
</span>
<input type="email" />

The Label/Field foundation owns reusable form-label, description, error, required, disabled, and validation relationships. Typography only supplies presentation.

Styling

Typography customization stays in the Web styling foundation, so every framework port sees the same result. Use public CSS custom properties for system-wide decisions and the stable variant hook for application-specific roles.

Font families

--vf-font-family-sansAa — Product interface
--vf-font-family-serifAa — Editorial voice
--vf-font-family-monoAa — 0123456789
--vf-font-family-displayAa — Display expression

Use a custom font

Load fonts with ordinary @font-face rules, then remap the public family token in the appropriate theme scope. VyrnForge does not require a font-loading runtime.

@font-face {
  font-family: 'Brand Sans';
  src: url('/fonts/brand-sans.woff2') format('woff2');
  font-display: swap;
}

:root {
  --vf-font-family-sans: 'Brand Sans', system-ui, sans-serif;
  --vf-font-family-display: 'Brand Sans', system-ui, sans-serif;
}

Add or disable a variant

Applications can extend the shared TypeScript registry once in @vyrnforge/web/text. React, Angular, and Vue then receive the same narrowed or extended TextVariant type.

declare module '@vyrnforge/web/text' {
  interface TextVariantOverrides {
    poster: true;
    heading: false;
  }
}

Style the custom role with ordinary CSS. No JavaScript theme provider or runtime registration is required.

[data-vf-text][data-vf-text-variant="poster"] {
  font-size: clamp(3rem, 7vw, 6rem);
  font-weight: var(--vf-font-weight-bold);
  letter-spacing: var(--vf-letter-spacing-tighter);
}

Framework API

All framework surfaces consume the same TextVariant vocabulary and Web styling contract. Only the syntax for choosing the native element changes.

SurfaceHow to use TextSemantic element
Native WebApply data-vf-text and data-vf-text-variant.You author the native element directly.
React<Text as="h2" variant="heading-lg" />as is explicit; default is span.
Angular<h2 vfText variant="heading-lg">The directive decorates the authored host element.

CSR and SSR

Text has no browser-only runtime. React, Angular, and Vue preserve native semantic elements during SSR; Native Web requires no hydration. Custom variant typing is compile-time only and adds no client registration step.

Do / Don't

Do

  • choose semantic HTML before visual treatment;
  • use explicit role names such as heading-md and body-sm for new work;
  • customize shared typography through public tokens;
  • use TextVariantOverrides for application-specific roles.

Don't

  • treat display-lg as meaning h1;
  • create framework-specific typography scales;
  • style private --_vf-* implementation variables;
  • introduce a JavaScript theme runtime just to change fonts or type values.

Testing guidance

Test observable typography behavior rather than private implementation details.

  • Assert the rendered native element when semantics matter.
  • Assert the public data-vf-text-variant hook or framework variant API.
  • Use browser evidence for computed typography only when visual values are part of the contract being tested.
  • Verify custom variants can be typed and styled through the public extension points.
  • Do not couple application tests to private --_vf-* variables.

Compatibility

The richer role vocabulary is additive: existing body, body-sm, label, title, and heading usages remain supported. Custom disabling narrows TypeScript acceptance for the consuming application but does not remove built-in CSS from the distributed package. Broader browser and release qualification remains governed by VyrnForge compatibility evidence rather than inferred from this page.
