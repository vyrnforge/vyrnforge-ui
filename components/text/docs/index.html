Text provides VyrnForge's extensible typography system while preserving native HTML semantics. Styling is opt-in through canonical Web hooks; visual typography never decides whether content is a heading, paragraph, label, or other semantic element.

Overview

Choose the correct semantic HTML element first, then apply a visual role. The built-in scale covers display, heading, title, body, label, caption, and overline treatments. Existing body, label, title, and heading names remain compatibility aliases.

Installation and imports

Load @vyrnforge/web/styles/text.css for canonical styling. Native Web uses the documented data hooks directly. React imports Text from @vyrnforge/react/text, Angular imports VfTextDirective from @vyrnforge/angular/text, and Vue imports Text from @vyrnforge/vue/text.

Quick start

Framework conveniences preserve the authored native element. For example, a visual display-lg treatment can be applied to an h1, while body-md can be applied to a p.

Anatomy

Text has two deliberately independent parts: the native semantic element chosen by the consumer and the VyrnForge visual role applied through data-vf-text plus data-vf-text-variant. Framework conveniences only compose those two parts; they do not create a separate typography runtime.

Variants and sizes

The primary visual-role vocabulary is display-lg, display-md, display-sm; heading-lg, heading-md, heading-sm, heading-xs; title-lg, title-md, title-sm; body-lg, body-md, body-sm; label-lg, label-md, label-sm; plus caption and overline. The suffix is part of the visual role rather than a separate component-size axis. Variant names describe presentation, never document structure.

State

Text has no semantic state API of its own. Disabled, invalid, required, selected, pressed, busy, or other state belongs to the owning semantic element or component. Typography variants must not encode application state indirectly.

Behavior

Text applies token-driven typography to an opted-in native element and otherwise leaves document behavior unchanged. Display roles use CSS-first fluid sizing with clamp(); other roles resolve to shared public typography tokens through the canonical Web stylesheet.

Interaction

Text adds no pointer, keyboard, focus, selection, or event behavior. If text participates in an interaction, the native element or owning Button, Link, form control, or composite component remains responsible for that interaction contract.

Accessibility

A heading-looking span remains a span, and an h2 remains an h2 regardless of visual treatment. Text adds no role or ARIA behavior. Consumers must choose native document semantics first, and the typography scale remains rem-based so browser text-size preferences continue to participate naturally.

Forms

Text does not define form labeling, validation, required state, descriptions, or errors. A real form label must remain a native label with the appropriate association. The Label/Field foundation owns reusable form relationships; a Text visual role may style their text without replacing those semantics.

Styling

The public foundation includes sans, serif, mono, and display font-family tokens; sizes from xs through 6xl; regular, medium, semibold, and bold weights; multiple line-height roles; and letter-spacing roles. Themes may remap these CSS custom properties through the normal VyrnForge cascade. Applications may load fonts with ordinary @font-face rules and remap --vf-font-family-sans, --vf-font-family-serif, --vf-font-family-mono, or --vf-font-family-display in a theme scope.

TypeScript consumers can extend the shared variant registry once in @vyrnforge/web/text. Framework ports consume that same type, so a custom variant becomes available consistently in React, Angular, and Vue. Setting a built-in key to false removes it from the typed API. Runtime styling for a custom variant is ordinary CSS targeting the stable data-vf-text-variant hook; no JavaScript theme registry is required.

declare module '@vyrnforge/web/text' {
  interface TextVariantOverrides {
    poster: true;
    heading: false;
  }
}
[data-vf-text][data-vf-text-variant="poster"] {
  font-size: clamp(3rem, 7vw, 6rem);
  font-weight: var(--vf-font-weight-bold);
}

Framework API

SurfaceText API
Native WebApply data-vf-text and data-vf-text-variant to the correct native element.
ReactText accepts as and variant plus native HTML attributes. as defaults to span.
AngularVfTextDirective uses vfText to attach the contract and the separate variant input to choose presentation; the authored host element remains unchanged.
VueText accepts as and variant and forwards ordinary attributes to the rendered native element.
ElementsNo custom element is provided. Native HTML already supplies the semantic text elements, so Elements consumers use the Native Web contract.

CSR and SSR

Text has no browser-only runtime. React, Angular, and Vue preserve native semantic elements during SSR; Native Web requires no hydration. Custom variant typing is compile-time only and does not add a registration or hydration step.

Examples

The Quick start example demonstrates the shared Text contract across Native Web, React, Angular, and Vue. Custom application variants use the same native element and stable CSS hook, so examples do not need a framework-specific theming API.

Do / Don't

Do choose semantic HTML first, use built-in role names for reusable system typography, customize fonts and visual values through tokens, and use TextVariantOverrides for application-specific variants. Don't use a visual variant as a substitute for heading level or form-label semantics, create framework-specific typography systems, or require a JavaScript theme registry for styling.

Testing guidance

Assert the rendered native tag, variant hook, cross-port type vocabulary, custom-variant augmentation, SSR output, and computed typography where browser evidence is useful. Verify consumer CSS can style a custom variant through the public hook. Do not couple tests to private --_vf-* variables.

Compatibility

The richer role vocabulary is additive: existing body, body-sm, label, title, and heading usages remain supported. Custom disabling narrows TypeScript acceptance for the consuming application but does not remove built-in CSS from the distributed package. Broader browser and release qualification remains governed by VyrnForge compatibility evidence rather than inferred from this page.
