AppShell composes authored application regions without owning routing, authentication, data, permissions, or product workflow state.

Overview

Use AppShell for the stable application frame around authored header, navigation, main content, and optional footer regions. It standardizes shared structure and styling hooks while leaving product content and application policy to the consumer.

Installation and imports

Import from the framework-specific /app-shell subpath and load @vyrnforge/web/styles/app-shell.css, or load the aggregate @vyrnforge/web/styles.css.

Quick start

Anatomy

AppShell exposes authored Header, Body, Navigation, Main, and optional Footer regions. Header tools, search, account controls, breadcrumbs, and other product UI are composed as children rather than becoming shell configuration.

State

AppShell owns no route, authentication, tenant, permission, or application-data state. Consumers own those concerns and render the appropriate authored content into shell regions.

Behavior

The default body layout provides a navigation column and flexible main content region, then collapses to one column at narrow viewport widths. Applications that need overlay navigation should compose an accepted Drawer or other lower-layer surface instead of relying on a shell-specific overlay manager.

Accessibility

Use the semantic Header, Main, and Footer regions exposed by the framework port and preserve meaningful source order. Navigation content should contain its own named navigation landmark. AppShell does not invent hidden labels, reorder focus, or add positive tabindex values.

Styling

Canonical styling is owned by @vyrnforge/web, uses shared tokens and logical properties, and exposes data-vf-app-shell* hooks. Consumers may extend application-specific sizing and composition through ordinary CSS without replacing the shared semantic structure.

Framework API

React and Vue expose semantic region components, Angular exposes standalone directives on authored semantic hosts, and Elements exposes explicitly registered sibling custom elements. All ports implement the same region meanings without introducing framework-router types.

CSR and SSR

AppShell imports are server-safe. Static structural layout requires no client JavaScript; application-specific responsive overlays or product controls hydrate according to the lower-layer components they compose.

Do / Don't

Do use AppShell for reusable application structure. Don't put router configuration, route guards, authentication, authorization, tenant resolution, data fetching, application state, or product workflow logic into the shell.

Testing guidance

Test landmark structure, semantic source order, persistent and narrow layouts, LTR and RTL presentation, focus visibility, forced-colors behavior, SSR safety, and any composed responsive navigation behavior.

Compatibility

React, Angular, Vue, and Elements implement sibling AppShell ports, with Native Web providing the canonical shared CSS contract.
